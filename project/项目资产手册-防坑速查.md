## 〇、先定性：这个项目到底沉淀了什么

按我的模型推——一个项目值不值得沉淀，看它留下的是"一次性成果"还是"可迁移资产"。本次留下三笔真资产：

| 资产 | 内容 | 迁移价值 |
|---|---|---|
| **架构资产** | 数据与视图分离 + 任意深度递归 + 不可变基线 + 三轨数据兜底 | 任何"树形可视化 + 内容管理"项目直接搬 |
| **数据资产** | v2 五块解析结构 + 校验器 + 幂等注入流水线 | 任何"批量内容工程"直接搬 |
| **工程资产** | 原子部署 + 四重禁缓存验证 + 分科按需加载 | 任何"静态站 + CI 自动发布"直接搬 |

**一句话心法**（先把结论甩这儿）：

> **先存基线再动刀，数据视图两分开；派生字段不手写，因题择法不泛化；原子提交一次过，禁缓存才验真。**

## 六、复盘框架（按我的模型推）

用解题的那套思维工具回看整个项目，四步闭环：

1. **定性先行**：先答"这是什么项目"——树形可视化 + 内容工程 + 静态发布，三件事叠在一起，所以坑分三类来治。
2. **找主要矛盾**：真正的杠杆是"数据与视图分离"（3.1），其余 UI、部署都是在这个地基上盖的。地基对了，后面都顺。
3. **出题人视角找坑**：把每次翻车当"出题人挖的坑"——手写答案、写死宽度、缓存假阳性，都是看似没问题、实则必踩的陷阱。提前列铁律，就是提前识坑。
4. **复盘成资产**：踩过的坑不写下来就是白踩。固化为脚本 + 校验 + 这份手册，下次同类项目直接调用，这才叫复利。
