## 一、项目概览与演进路线

整个项目不是一次性设计出来的，而是**由一连串具体问题驱动、逐层演进**的结果。理解这条路线，比记住任何一个具体知识点更重要。

```text
原始单文件页面（1.59MB / 15720 行）
   │  分析：它由什么组成？对我有什么用？
   ▼
存档基线 baseline.html ──► 最小剥离 minimal.html（验证"换数据不换引擎"）
   │
   ▼
UI 改造 optimized.html（多轮迭代：配色、筛选、弹窗、练习、适配）
   │  发布 demo 链接验证真实效果
   ▼
数据驱动：data.json / data.js 从 HTML 抽离（验证"改数据不改代码"）
   │
   ▼
GitHub Pages 自动部署（动态链接，push 即上线）
   │
   ▼
后端动态化：FastAPI + SQLite 在线管理真题
   │
   ▼
AI 录入工作流：上传 PDF + 报题号 → 自动解题入库
   │
   ▼
灌注真实数据：914 节点 / 186 例题，完整五科知识树
   │
   ▼
交互收尾：默认收起 / 移除缩放按钮 / 全屏 / 收起展开
```

**一句话概括演进逻辑**：先把"能用的东西"拆成"可维护的结构"，再给结构接上"持续更新的能力"，最后用真实数据验证整条链路。

## 二、架构演进的四个阶段

### 阶段 1：解构期 —— 从巨石文件中提炼核心引擎

原始页面是一个把数据、样式、渲染逻辑全部塞在一起的 1.59 MB 单文件。第一步不是改造，而是**存档 + 剥离**：

| 动作          | 产物                        | 目的                       |
| ----------- | ------------------------- | ------------------------ |
| 原样存档并校验 MD5 | `baseline.html`           | 建立不可变基线，任何改动可回溯对比        |
| 剥离核心渲染能力    | `minimal.html`            | 只保留建树、布局、贝塞尔连线、平移缩放、展开收起 |
| 用两套不同数据驱动   | 截图 `shot-dataset-b.png` 等 | 证明"引擎不变，数据可换"            |

**经验**：面对复杂的现成系统，先做"减法实验"——把非核心功能全部拿掉，看剩下什么能独立工作。这一步用 20 KB 的代码证明了整个项目最关键的架构假设，代价极低。

### 阶段 2：数据驱动期 —— 让内容与代码解耦

把 `optimized.html` 里内嵌的 `PALETTE / SUBJECTS / ORDER / EX()` 抽离为独立的 `data.json`，前端通过 `loadData()` 加载。

设计了**三级数据源兜底**：

```js
function loadData(){
  const useApi = new URLSearchParams(location.search).get('api')==='1';
  if(useApi){
    return fetch('/api/tree').then(applyPalette)
      .catch(()=> fetch('data.json').then(r=>r.json()).catch(()=>window.MM_DATA));
  }
  return fetch('data.json').then(r=>r.json())
    .catch(()=> window.MM_DATA || Promise.reject(new Error('无法载入数据')));
}
```

| 优先级 | 数据源                       | 适用场景              |
| --- | ------------------------- | ----------------- |
| 1   | `?api=1` → `/api/tree`    | 后端在线管理模式          |
| 2   | `data.json`               | 静态托管（HTTP 访问）     |
| 3   | `window.MM_DATA`（data.js） | 本地 `file://` 双击打开 |

**经验**：兜底链的设计顺序是"动态 → 静态外链 → 内联兜底"。每一层都解决一类特定部署环境的问题，缺一层就会在某个场景下白屏。特别是 `file://` 场景，浏览器会阻止 `fetch` 本地 JSON，必须有 script 标签引入的内联数据兜底。

### 阶段 3：后端动态期 —— 从静态快照到可维护系统

静态数据每次更新都要重新发版，不适合持续维护。于是引入 FastAPI + SQLite：

- **三张扁平表**：`subjects`（科目）、`nodes`（节点，`parent_id` 表达层级）、`examples`（例题，`node_id` 挂接）
- **API 层组装树**：`/api/tree` 把关系表递归组装成前端可直接消费的嵌套 JSON，并返回 `__id` / `__level` 供管理台使用
- **管理台**：`admin.html` 提供科目/节点/例题的可视化增删改

**经验**：关系型表存树 + API 组装，是"既要可查询维护、又要前端树形渲染"的经典解法。把树的组装放在后端，前端保持纯粹——这让同一个画布既能吃静态 JSON，也能吃 API 返回，验证了解耦的价值。

### 阶段 4：数据灌注期 —— 用真实数据检验全链路

从 `baseline.html` 解析出完整 `SUBJECTS`（约 883 KB），重建完整知识树：

```text
总计: 914 节点 · 186 例题
层级分布: L1=42 · L2=198 · L3=431 · L4=243
```

| 科目   | 模块 | 节点  | 例题 |
| ---- | -- | --- | -- |
| 判断推理 | 5  | 205 | 54 |
| 常识应用 | 15 | 292 | 12 |
| 数量关系 | 14 | 190 | 57 |
| 言语理解 | 3  | 129 | 40 |
| 资料分析 | 5  | 56  | 23 |

**经验**：真实数据总会暴露示例数据掩盖的问题。这次就暴露了"前端 `buildTree()` 只支持到 L3"的隐藏缺陷——真实树有 L4 方法层，原逻辑会丢失或错位。修复方式是把建树改成任意深度递归。**永远用最接近生产的数据做最终验证。**

## 三、核心技术经验

### 3.1 数据与视图分离是最大的架构杠杆

整个项目最值钱的决策，就是把内容（`SUBJECTS`）与渲染引擎彻底分开。带来的直接收益：

- 换数据不换代码 —— 同一引擎渲染五科、渲染示例、渲染真实数据
- 静态/动态数据源可切换 —— 只改数据加载入口
- 领域无关 —— 换掉数据就能把行测思维导图改成任意主题的思维导图

### 3.2 领域无关渲染引擎

画布引擎（建树、布局、贝塞尔连线、平移缩放、展开收起、hover、弹窗）完全不感知"行测"这个概念。它只认一个通用的树结构：`{name, children, examples, color}`。

**判断一个引擎是否真正解耦的测试**：给它两套完全不同主题的数据，如果能正常工作且无需改一行引擎代码，解耦就是成功的。

### 3.3 任意层级递归优于写死层级

最初的 `buildTree()` 按 L1/L2/L3 写死层级，遇到 L4 就崩。改为递归后，代码更短且更健壮：

```js
function addChildren(list, parent, level, color, mod){
  (list||[]).forEach(item=>{
    const node = makeNode(name, level, color, parent, {star, examples, mod});
    if(item.children && item.children.length){
      addChildren(item.children, node, level+1, color, mod);  // 递归任意深度
    }
    parent.children.push(node);
  });
}
```

**经验**：凡是处理树形/层级结构，默认就写递归，不要假设最大深度。

### 3.4 默认收起 vs 全部展开的交互设计

最终版的收起逻辑把"默认状态"和"批量控制"分开处理：

```js
// 建树时：默认全部收起
root._open=true;
(function setOpen(n){n.children.forEach(c=>{c._open=false;setOpen(c)})})(root);

// 工具栏按钮：一键切换整树
function setAllOpen(open){
  (function rec(n){n.children.forEach(c=>{c._open=open;rec(c)})})(rootNode);
  rootNode._open=true;   // 根节点必须保持展开，否则整棵树不可见
  render();fitView();
}
```

**坑点**：`rootNode._open=true` 这行不能省。如果连根节点都收起，整棵树将完全不可见（因为可见性由父链的 `_open` 决定）。

## 四、UI/UX 迭代经验

UI 经过多轮反馈才定型，沉淀出几条设计原则：

### 4.1 "主体优先"原则

用户反复强调"主体应该是思维导图"。最初右侧有常驻的筛选面板和统计卡，占据大量空间。最终改为：

- **常驻面板 → 浮层**：筛选改为顶栏 `▽筛选` 按钮唤出的轻量浮层，点外部/ESC 关闭
- **统计信息 → 一行淡字**：压到画布左下角 `#statLine`，不抢占视觉

**经验**：当工具控件与内容主体争夺空间时，优先把控件"藏起来"——用触发式浮层替代常驻面板。

### 4.2 图例与"统计图感"的取舍

用户反馈左侧配色图例和筛选区"太像统计图"。处理方式是移除配色比例图例、把题源/对错改成纯文字分段控制器。

**经验**：知识工具类产品要克制"数据可视化"冲动。用户来这是看知识结构的，不是看统计图表的。

### 4.3 弹窗尺寸与触屏适配

例题弹窗经过多轮调整：620px → 900px → `min(1200px, 94vw)`。最终方案：

```css
#detailBox{
  width:min(1200px,94vw);
  max-height:92vh;
}
@media (pointer:coarse){        /* 触屏设备单独放大点击区 */
  .ex-opt{padding:12px 14px;font-size:15px}
  .ex-btn{padding:10px 16px}
  ...
}
```

**经验**：用 `min(固定值, 视口百分比)` 做弹性尺寸；用 `@media (pointer:coarse)` 而非屏幕宽度来区分触屏——它更准确地反映"是否需要大点击区"这一真实需求。

### 4.4 例题弹窗的左右分栏改造（方案 B）

弹窗从"单列长卡片 + 内联折叠答案"改造为**左右分栏**：

```
弹窗(固定高度)
├─ 左栏 做题区 50%  ── 题号导航条(单行横滚) + 题干/配图/选项/判定/按钮
└─ 右栏 解析区 50%  ── 答案徽章 + Tab[解题步骤|解法|深度解析|选项排除]
```

四个关键设计决策：

1. **答案从卡片内联移到右栏独立**：左栏只管做题，右栏只管解析，职责分离。点「看解析」或练习判题后，右栏才渲染对应题解析，默认显示占位提示。
2. **解析按 Tab 分层**：不再一次平铺 5 个板块（信息墙），改为按需生成 Tab——`steps`→`解法`→`深度解析`→`exclude`，**只显示有内容的**，默认激活第一项。这解决了"steps 与 analysis 内容重叠、视觉无主次"的问题。
3. **打通「练习→解析」链路**：`judge()` 判题后自动调用 `activateEx()` 展开右栏解析，用户不用再手动点一次。
4. **多题联动**：题号导航条 + 卡片高亮 + `←/→` 键盘切题，解决"单节点挂 6 题只能滚"的痛点。

**踩坑（重要）**：改造初期用 `max-height:92vh` 给弹窗，导致 flex 子项在窄屏上下堆叠时高度失控——左栏内容把容器撑到 **24115px**，右栏被挤到屏幕外。根因是 `max-height` 不给 flex 子项提供确定高度基准。修复：**改用固定 `height:min(860px,92vh)`**，窄屏堆叠时两栏用 `flex:0 0 50%` + `min-height:0` 按百分比分配高度。另：题号导航条最初 `flex-wrap:wrap` 让 54 个按钮换行占 146px，改为 `nowrap + overflow-x:auto` 单行横滚后降到 48px。

### 4.5 工具按钮的取舍逻辑

最终工具栏：`试卷下拉 · 筛选 · 便签 · 收起 · 展开 · 回到根 · 适应视图 · 全屏`。

- 移除了放大/缩小按钮 —— 因为缩放已有 `Ctrl+滚轮` 和双指手势，点击按钮是冗余
- 保留了全屏、收起展开 —— 这些没有手势替代，且高频

**经验**：新增一个按钮前，先问"是否已有等价交互"。有手势替代的点击按钮可以砍掉，让工具栏更轻。

### 4.6 试卷筛选维度：从 baseline 找回丢失的功能

原版 baseline 有「按试卷筛选例题」下拉框，优化版迭代中丢失。用户要求补回工具栏。数据里**没有独立的卷名字段**，试卷信息只藏在 `src`（如 `2026广东省考真题 第46题`），因此用 `volOf(src)` 截取 `" 第"` 之前作为卷名——这是原版已有的成熟逻辑，直接复用。

实现要点：

1. **筛选判定叠加**：在 `exMatch()` 末尾加第三条件 `if(EXVOL && volOf(ex.src)!==EXVOL) return false;`，与题源(真题/模考)、对错形成 AND 三维筛选。  
   |  |  |  |  
   | --- | --- | --- |
2. **缓存 key 必须同步**：`countEx()` 的缓存 key 从 `EXFILTER+'|'+EXSRC` 改为加 `|EXVOL`。**踩坑**：该函数虽接收 `key` 参数，内部却重新计算 `const k=...`，参数实际被忽略——必须改函数内那一行，改调用处无效。否则切卷后节点「例题 N」徽标不刷新。弹窗走 `nodeExamples()→exMatch()` 实时计算、无缓存，自动跟随。
3. **切科重填**：卷列表按当前科目聚合（各科卷不全一致，如常识应用缺 2025真题）。但优化版没有 baseline 的 `window.__volFill` 钩子，改为在 `switchSubject()` 和 `boot()` 的 `rootNode=buildTree()` 之后直接调 `fillVolSelect()`。注意 `loadData().then(boot)` 异步，脚本解析期 `rootNode` 为 null，不能像 baseline 那样 IIFE 立即填充。
4. **无记忆（用户决策）**：不同于 baseline 用 localStorage 存偏好，本次只保留当前生效值 `EXVOL`；切科后当前卷在新科目不存在则回「全部」，刷新也回「全部」。更轻量，避免跨会话的状态残留。

**经验**：给筛选系统加一个维度时，要同时改三处——判定函数、缓存 key、派生数据重填入口——漏掉缓存 key 会导致"数据变了但界面徽标没变"的隐蔽 bug。

### 4.7 设计稿落地到真实前端：皮肤与逻辑分离

把独立的「朱批·审题台」视觉设计稿移植到主文件 `canvas.html` 弹窗时，核心原则是**只换皮肤、不动逻辑**：

1. **class 前缀隔离**：设计稿的 `.step/.err/.seal` 等通用类名会与画布/旧弹窗冲突。所有新样式统一加 `zp-` 前缀，并在弹窗根节点挂 `zp-mode` 开关类——渲染 v2 解析时加、回退旧结构时移除，两者互不污染。
2. **判题逻辑零改动**：`judge()`、选项状态类（`sel/locked/correct/wrong/pickable`）、所有 `data-*` 属性一行不动，只用 CSS 重新定义这些类的视觉（答题卡圆点、朱砂选中、竹青正确）。这样视觉改造对判题零风险。
3. **v2 优先 + 旧字段回退**：`renderAns()` 开头判断 `ex.solution` 是否存在——有则渲染朱批五块（答案印章/步骤时间轴/错因/深解/策略），无则走原深色 Tab。186 道题只注入了 5 道样板 solution，其余照常显示，平滑过渡。
4. **数据注入三处**：样板数据要同时写进 `data/subjects/p1.json`、`data.json`、`data.js`（后者是 `window.MM_DATA=...` 包裹格式，需去前缀解析后再回填），保证分科加载、静态兜底、本地 file:// 三条路径都能看到新解析。
5. **验证脚本要兼容双结构**：原来的 `.ans-tab` 断言在 v2 题上会超时误报。改为 `wait_for_function` 同时接受 `.ans-tab` 和 `.zp-seal`——**测试假设要跟着功能演进更新，否则"绿灯"变"误报"**。

**踩坑**：本地判题测试一度 4 项 FAIL，原因是测试脚本直接点选项——但真实流程必须先点「练习」按钮给选项加 `pickable` 并绑定 onclick。**测试要还原真实交互路径**，不是凭空点 DOM。

### 4.8 性能诊断：先定位瓶颈，再谈优化

用户反馈"打开慢"，用 Performance API 实测各阶段而非凭感觉：

| 阶段           | 冷启动    | 热启动   |
| ------------ | ------ | ----- |
| TCP+TLS 建连   | 1941ms | 418ms |
| 19KB HTML 下载 | 4626ms | 212ms |
| 首屏可交互        | 6986ms | 869ms |

**结论**：热启动 <1s 证明代码不慢，瓶颈全在 GitHub Pages 境外链路的冷连接（建连+下载占 6.5s）。页面无任何外部阻塞资源，分科加载正常。这是**网络问题不是代码问题**——先定位再动手，避免盲目优化前端。

加速方案（专家评估）：

- **零成本**：`preload p1.json` 让其与 manifest 并行，省 1 个 RTT，冷启动约 7s→6~6.5s，改善有限（受境外链路封顶）。
- **根治（推荐）**：复用已有广州 OSS bucket 开静态托管 + CDN + 已备案域名，冷启动 7s→**1~1.5s**；流量费几乎为 0（项目仅 585KB）。

## 五、发布与部署经验

### 5.1 先发布 demo 验证，再建正式链路

先用静态托管发布一个 demo 链接，在桌面和手机上实测配图、弹窗、交互都正常，再投入做正式的自动部署。**先用低成本方式验证"值不值得做"，避免过早投入重基础设施。**

### 5.2 网络受限时用 API 替代 git push

这是本次最有价值的运维经验。环境现状：

- `github.com:443` 超时，`git push` 不可用
- `api.github.com` 可访问

解决方案：改用 GitHub Contents API 上传文件：

```bash
gh api repos/{owner}/{repo}/contents/{path} \
  --method PUT --input payload.json
# payload 需包含: message / content(base64) / branch / sha(更新时必带)
```

要点：

- 更新文件必须带原文件的 `sha`（先从 GET `/contents/{path}` 获取）
- 大文件（1.1 MB）用 Python 构造 JSON payload 写到临时文件，再 `--input` 读取，避免命令行长度限制
- 配置好 `gh auth login` 后，token 由 gh 管理，无需在命令中暴露

### 5.3 私有仓库不支持 Pages

GitHub 免费方案下，私有仓库无法启用 Pages。曾因此报错 `Your current plan does not support GitHub Pages for this repository`，改为 public 仓库后成功。**建仓库前先确认 Pages 的前置条件。**

### 5.4 部署验证要等 workflow 真正完成

触发 `gh workflow run deploy.yml` 后，需轮询确认 `status=completed / conclusion=success`。曾出现刚上传 workflow 就触发导致失败的情况——**Pages 未正确开启时 workflow 会失败，先确保基础设施就绪。**

### 5.5 线上验证的"网络陷阱"

最后一次线上浏览器测试超时，原因是 1.1 MB 数据 + OSS 外链配图在沙箱网络下加载过慢，而非代码问题。解决技巧：**用 Playwright 拦截图片请求**（`route.request.resource_type == 'image'` 时 abort），只对画布逻辑做验证。

**经验**：当测试超时，先区分"逻辑错误"和"环境网络慢"。拦截非关键资源（图片）能快速隔离问题。


### 5.6 部署性能优化：从"25 次部署"到"1 次原子提交"

用真实 GitHub Actions 记录复盘部署过程，发现问题不在 Pages 本身，而在**上传方式**：

| 指标            | 优化前                                                  | 优化后                                                                   |
| ------------- | ---------------------------------------------------- | --------------------------------------------------------------------- |
| 一次改动触发的部署次数   | 每传 1 个文件触发 1 次（data.json / data.js / index.html 各一次） | 8 个文件 1 次 commit、1 次 push、**1 次部署**                                   |
| 历史部署记录        | 25 次 run / 16 次有效提交                                  | 新增 1 次即 1 次                                                           |
| 并发冲突          | 4 次 cancelled、2 次 failure                            | 0（workflow 加 `concurrency: {group: pages, cancel-in-progress: true}`） |
| workflow 执行时长 | 平均 21s（排队 0s）                                        | 15s                                                                   |

根因：早期用 `PUT /repos/{repo}/contents/{path}` 逐文件上传，**每个文件一次 push = 一次 workflow**。三份重复下载（data.js/data.json）和固定 `sleep` 验证进一步放大耗时。

两个关键动作：

1. **原子上传**：用 GitHub **Git Data API** 在一次 commit 里提交所有文件。  
   流程：`GET ref` → `GET commit/tree` → 逐文件 `POST /git/blobs` → `POST /git/trees`（`base_tree` 复用原树，只覆盖变更文件）→ `POST /git/commits` → `PATCH /git/refs/heads/main`。  
   脚本：`tools/gh_upload_atomic.py`，凭证取自本地 `gh` 登录态，不硬编码 token；支持 `--dry-run` 先看计划。
2. **并发控制**：workflow 顶层加 `concurrency`，新部署自动取消旧部署，根治连续上传导致的 cancelled/failure。

**经验**：静态站点的"部署慢"多半是提交了太多次，而不是 Pages 慢。先数 `gh run list` 里一次改动对应几次 run，再决定是否上原子提交。

### 5.7 首屏按需加载：分科数据 + 事件驱动验证

数据拆分（`tools/split_data.py`）把 588 KB 的完整 `data.json` 拆成 `manifest.json` + 5 个科目文件，前端改为**先取清单、只下首科、切科再取**：

```
首屏: GET data/manifest.json (0.7KB) + data/subjects/p1.json (149.9KB) = 150.6KB
切科: 点到哪一科再 fetch 对应 p2~p5（按需，不预取）
兜底: manifest 缺失 → 完整 data.json；file:// 本地双击 → 动态注入 data.js
```

关键点：`data.js` 不再无条件 `<script>` 引入（原先线上白白多下 588 KB），只在 `file://` 且 fetch 失败时才动态注入。

线上 A/B 实测（同一浏览器环境，各 2 轮取稳定值）：

| 加载方式             | 首屏数据量    | domcontentloaded→节点渲染 |
| ---------------- | -------- | --------------------- |
| 分科按需加载           | 150.6 KB | 约 2–6 s（受 CDN/网络波动）   |
| 强制回退完整 data.json | 585.7 KB | 稳定 17–18 s            |

数据量下降 **74.4%**，加载时间从十几秒降到数秒级。`verify_deploy.py` 也改为事件驱动：`gh run watch` 等部署完成、`wait_for_function` 等节点数稳定替代固定 `sleep`、`page.route()` 拦截图片——7 项检查全通过，无长睡眠。

**经验**：验证脚本本身也会有 bug（曾把 Playwright `JSHandle` 直接做 `>` 比较而误报 FAIL，`wait_for_function` 的返回值须 `.json_value()` 转 Python 值）。测试失败时先判断是"功能错"还是"测试脚本错"。

## 六、数据工程经验

### 6.1 图片存储策略的权衡

图形推理等题目涉及图片。原版为 30 个 OSS 外链 + 14 处内嵌 base64；灌注真实数据后以树内 examples 为准，最终为 **44 道带图：29 个 OSS 外链 + 15 处内嵌 base64**。三种方案的权衡：

| 方案        | 优点    | 缺点              |
| --------- | ----- | --------------- |
| OSS 外链    | 省体积   | 依赖第三方稳定性，链接可能失效 |
| base64 内嵌 | 单文件便携 | 体积大             |
| 本地文件      | 稳定可控  | 需整套目录一起同步       |

**当时的决策：统一使用 OSS 外链，不做图片本地化。**（⚠️ 此决策已于 6.19 被推翻——OSS 欠费导致外链全挂，图片已全量迁回仓库 `assets/img/`，见 6.19 节。本节保留作为历史权衡记录。）

2026-11-18 已完成迁移：15 张内嵌图（6 jpg + 8 png + 1 svg，其中 URL 编码的 SVG 需特殊处理）上传到自有 OSS bucket `alibbxtbox` 的 `mm5/b64/` 目录，去重后实际上传 8 个文件。使用脚本 `tools/upload_b64_to_oss.py`（凭证走环境变量、自动去重、同步回填 data.json/data.js/数据库、上传前备份）。结果：

- 44 张带图全部为外链，内嵌图归零
- `data.json` 从 1.1 MB 瘦身到 394 KB
- 线上验证外链 HTTP 200、弹窗配图正常、零 JS 错误
- OSS 需为**公共读** bucket，否则外链打不开；前端对失效外链有兜底显示（虚线框 + "配图加载失败"）

跨设备结论留作参考：**相对路径本地文件可跨设备，但必须整套文件夹一起走**——该方案本次不采用。

**安全提醒**：上传所用 AccessKey Secret 已在对话中留痕，使用完毕应在阿里云 RAM 控制台禁用/轮换该密钥。

### 6.2 AI 录入工作流

用户的核心诉求是"上传试卷 PDF + 报题号，由 AI 完成录入"，而不是手动填表。建立的工具链：

```text
上传 PDF → 按题号提取切块 → AI 补全答案/解析 → 结构化题目 → 入库 API → 画布显示
```

| 工具                     | 职责                                                    |
| ---------------------- | ----------------------------------------------------- |
| `tools/pdf_extract.py` | `--dump-all` 列题号 / `--nums 3,5,12` 提取 / `--imgdir` 提图 |
| `tools/ingest.py`      | `--file questions.json` 批量导入 / `--node-id` 定位节点       |

**经验**：把"人工录入"改造成"人只做选择题号这种低认知负担的事，AI 做解题和结构化"，是这类数据录入场景的正确分工。

### 6.3 PDF 解析的两个真实坑

1. **中文乱码**：reportlab 生成的测试 PDF 中文提取为 `\x00`——这是测试 PDF 构造问题，不是提取器逻辑问题。真实试卷需实际上传后再验证。
2. **行内选项未拆分**：`A. 96 B. 100 C. 104 D. 108` 被当成题干。修复用正则按 `([A-D])\s*[.．、:：]\s*` 拆分。

### 6.4 工作版 + 分发版双轨制

灌注真实数据后，数据出现多副本：

- `mindmap-server/`：完整数据 + 数据库（工作版）
- `mindmap-demo/`：完整的 `index.html` + `data.json` + `data.js`（分发版）
- `mindmap-canvas/`：早期原型 + 旧的 36KB 数据（历史存档）

**教训/提醒**：多副本同步时容易遗漏。本次 `mindmap-canvas/data.json` 仍是旧的小数据，与另两处的完整数据不一致。建议明确"唯一的权威数据源"，其余都是派生产物，并在每次更新后校验 MD5。

### 6.5 数据体积的代价

灌注真实数据后 `data.json` 从 36 KB 涨到 1.1 MB。Pages 仍能加载，但体积增长明显。若生产环境对首屏速度敏感，可考虑按科目拆分数据、按需加载。

### 6.6 教训：灌注真实数据时丢失了 steps / exclude 字段

2026-11-18 发现：用户反馈"导图好像没有解题步骤"。排查后确认——**原始 baseline 的 186 道题里有 179 道带 `steps`（分步解题步骤）、158 道带 `exclude`（选项排除分析），但 `rebuild_full.py` 灌注时只映射了 solve/analysis/img，把这两个字段丢了**。虽然 7 道图形推理题原本就没有 steps（原版也是），但其余 179 道的精华步骤全部缺失。

修复过程：

1. 从 baseline 花括号配对解析完整 SUBJECTS（883 KB），提取 179 份 steps + 158 份 exclude
2. 用「题干 + 选项 + 答案」规范化键匹配回填数据库和 data.json（179/186 命中，7 道图形题本就无 steps）
3. 数据库 `ALTER TABLE` 加 `steps` / `exclude` 两列；改 `server.py` 的模型、序列化、入库/更新 SQL 让 API 也输出这两个字段
4. 前端弹窗增加「🪜 解题步骤」（带序号）和「🔍 选项排除」（对/错标色）两块展示
5. 逐字段对比确认原有字段零丢失零改动，仅新增 steps/exclude

**核心教训**：从富数据源向精简结构迁移时，必须做**字段清单对比**——列出源数据的所有字段，逐一确认目标是否保留。只盯着"我知道的重要字段"（solve/analysis）会静默丢失其他有价值的字段（steps/exclude），而且这种丢失在示例数据阶段完全看不出来，直到用户用真实场景检验才暴露。这与"用真实数据做最终验证"（方法论第 4 条）是同一个道理的又一次印证。

部署插曲：短时间连续触发两次 Pages workflow 导致并发冲突、最后一次 failure；重新单次触发后 success。**连续上传多个文件后应合并为一次部署触发，避免并发。**

### 6.7 真实试卷录入闭环：第71题从 PDF 到线上朱批解析

2026-11-18 用用户上传的《2025广东省考行测（网友回忆版）》PDF（25 页/90 题/31 道错题）跑通了完整录入闭环，选定**资料分析第71题**（用户错选 B、正确 A）作为首道真实录入题。挂载到 `资料分析 > 增长 > 其他 > 累计求当期：当期值=本期累计−上期累计`。

关键决策与踩坑：

1. **资料分析题依赖材料表格，文本层不含表格**：`pdf_extract.py` 抽第71题时 `q` 为空、选项混入下一题。改用 `--imgdir` 把第20页表格图落盘，多模态读出数据（2023年12月 4055.97、1~~12月 47494.86、2022年12月 3741.65、1~~12月 44882.92）。材料最终**两案都上**：①表格数据文字内嵌进题干（自包含兜底）；②表格截图传 OSS 填 `img`（后补，用户要求）。凭证未落盘、只在对话历史里，用 `upload_q71_material.py` 从 jsonl 提取后内存使用（不回显），传到 `mm5/q71/`，内容 MD5 命名。前端配图在左栏卡片、朱批解析在右栏，互不干扰。
2. **答案 = 1~12月累计 − 12月 = 47494.86 − 4055.97 = 43438.89 亿元 ≈ 4.34 万亿元 → A**，用户错选 B（4.43，4.34 的数位颠倒）。解析里专门点破这个坑。
3. **数据一致性陷阱（最值得记）**：5 道 v2 样板此前只在 demo 分发文件里，权威源 `server/data.json` 的 `solution` 数为 0。直接往源里注入新题再 split，会把 p1 样板整批冲掉（164623B→153503B）。修复：以 demo 完整对象为基准并入新题，**同时覆盖**源 + demo/data.json + demo/data.js 三处，再 split，最后核对 p1 体积恢复。
4. **校验脚本自伤**：`validate_v2.py` 的 `iter_examples()` 把带 solution 的题数两遍（「题目数:2」实为 1），改为按对象 id 去重。
5. **幂等注入**：`inject_q71.py` 按 `src` 先删后加，重复跑不会产生重复题。
6. **`hit` 标签填反（用户发现）**：录入第71题时把 `hit` 手滑写成 `true`（做对），但 PDF 里正确 A/你的 B 是错题——线上显示「✅ 做对」，与 PDF 对不上。`hit` 唯一正确来源是 `set(正确答案)==set(你的答案)`，不能手填。做法：全文正则解析 PDF 的 90 组答案对（本卷 30 道错题），与导图 42 道 2025广东省考题逐一对照，只改冲突项（本次仅第71题 1 处）。前端左栏 `.ex-tag` 与朱批 `.zp-tag-*` 都由 `hit` 自动渲染，改数据即可。
7. **材料呈现按用户要求迭代**：先文字内嵌兜底 → 后传 OSS 截图 → 最后按用户要求「只留截图」，删掉题干里的数据文字、只留问题句 + `img` 外链。

验证：专项脚本 `verify_q71_final.py` 线上 PASS（❌做错标签、题干只剩问题句、材料图正常加载、朱批 ✕做错、零 JS 错误）；全量 `verify_deploy.py` 7/7 无回归。完整流程沉淀为 `/workspace/试卷错题录入工作流程.md`。

**核心教训**：录入流水线里，"数据摆放位置"和"题目本身"同等重要。多副本（源/demo/分科/js）任一处漏改，都会静默产生线上与预期不符的结果——**每次注入后必须做全量对账（总数 + 各科分布 + 关键文件体积），而不是只看新题那一点**。

### 6.8 把踩坑固化成脚本：ingest_v2.py 的工程化沉淀

第71题那一连串问题（hit 填反、样板被冲、材料截图、凭证读取）暴露的不是"某次手滑"，而是**流程本身允许手滑**。真正的解法不是下次更小心，而是让错误**没有入口**。于是把整条流水线固化成 `tools/ingest_v2.py`，两个核心防呆：

1. **hit 自动派生，从根上取消手填**：题目文件里根本没有 `ans`/`hit` 字段的入口——脚本从 `answers.json` 按题号取 `correct` 派生 ans、`set(correct)==set(mine)` 派生 hit，并强制校验 `solution.answer` 与派生 ans 一致。故意写错直接 FAIL、零文件写入。**教训**：易错字段不要"让人填对"，而要"让人填不了错"。
2. **样板防冲 + 幂等 + 对账**：以含全部样板的 demo 完整对象为合并基准（不碰权威源缺样板的问题），按 `src` 先删后加（重复跑 MD5 不变），覆盖 4 处后 split，跑全量 v2 校验 + 数据对账，可选原子部署。**教训**：把"每次记住要做的检查清单"写进脚本的默认路径，比写进文档管用。

**一个额外收获——纠正了历史误判**：早期统计说这份卷"31 道错题/答案对有 4 组缺失"，一度以为是跨页格式问题。重写解析器时发现粉笔 PDF 是**答案总表前置**结构（题号区在后、答案区在前），早期用"遇到答案行时 cur 停在哪个题号"的配对法只对了 23 题。改成**分别提取有序的题号/正确答案/你的答案三序列再按序 zip**后，90 题全解析、零歧义、30 道错题，逐题样本全部吻合。**教训**：数据"看起来对不上"时，先怀疑解析方法，别急着归因于数据缺失。

实测：derive-answers 90题/30错/零歧义；dry-run 在无 ans/hit 输入下正确派生 `ans=A/hit=做错`；故意写错 answer 被拦截；连跑两次 MD5 一致（幂等）。完整操作见 `/workspace/试卷错题录入工作流程.md` 的「零、v2 一键流水线」。

### 6.9 批量重写解析：从 1 道样稿到 49 道全覆盖

重写全部解析是典型的"大批量内容工程"，最忌一上来就铺开。本次走四步，把风险压到最低：

1. **先定样板，再谈批量**：从判断推理 54 道里挑第47题（图形推理·求同去异，有配图、两段式、代表性强）做 v2 五块样稿，套线上真实渲染函数出预览图给用户确认。**教训**：内容工程先立"标尺"，用户点头后再放大，比写完返工省十倍。

3. **配图题必须逐题读图**：17 道配图题（图形推理、六面体、三视图、截面、受力分析、电路、锋面雨、食物网）全部下载原图逐张核对，再据旧解析重写；不凭旧解析盲写——旧解析的 `solve`/`analysis` 是精准骨架，重构为五块时用它当"答案与定性"的锚，步骤/错因/策略再展开。**教训**：图不读不写；旧解析当锚不当终稿。
4. **注入—对账—部署—抽样验收闭环**：`batch_inject.py` 按 src 幂等覆盖 4 处数据文件，扩展词表加"支持项"适配"最不能支持"反向题；split 后对账逐字段一致、全库 55/55 零失败，原子提交一次部署（commit `aca4c375`），线上 7/7 通过，再抽 3 道不同类型出真实渲染样张验收。

### 6.10 弹窗交互：从"点看解析"到"打开即新UI"

用户反馈"要点解析才出新 UI，弹窗还小"。这次改动暴露两个典型坑：

1. **交互路径冗余**：原 `openDetail()` 打开时 `activeExIdx=-1`、右栏放占位提示，必须点"看解析/练习"才 `activateEx()→renderAns()` 渲染朱批。既然 v2 解析已成主路径，占位态就没意义了——改为打开末尾直接 `activateEx(0,false)`（第二参关掉首题的平滑滚动，避免弹窗刚开时晃动），占位符在无 solution 时由 `renderAns` 自动回退，无需用户多点一次。**教训**：主路径升格后，要回头删掉为旧路径准备的中间态。
2. **线上验证的缓存假阳性**：部署 workflow success、源码确认新串在/旧串 0，但 Playwright 首验仍是旧尺寸 1200×860、旧行为——是浏览器缓存了旧 HTML。破缓存（URL 加 `?v=时间戳` + `Cache-Control:no-cache`）后复验即 PASS（1440×960、打开即朱批、零报错）。**教训**：线上验证 FAIL 先别改代码， workflow success + 源码对得上时，优先怀疑缓存。

### 6.11 字号适配：左右栏"一大一小"怎么调

弹窗放大后新问题暴露：左栏题干 15px/选项 14px，右栏朱批正文却是一堆 9~10px 小字（步骤 10、错因 10、深度 10.5），视觉割裂。

改动用 `retune_font.py` 落盘（21 处），同步后原子部署（commit `3511c3a`），本地 + 线上 CDP 禁缓存双 PASS。

### 6.12 选项去方块：让页面不再被切成几块

### 6.13 用筛选器替代题号导航：结构性改动要理顺依赖

用户嫌题号导航（1/2/3 圆钮）和题目序号没用，要在标题栏加试卷筛选器。这是结构性改动，不是加样式。

### 6.14 重写数量关系57道：因题择法，别把一招当万能

### 6.15 重写资料分析 23 道：先划边界，再按材料组读图

用户拍板三件事：言语整体跳过（逻辑填空非本人强项）、本轮只做资料分析、先出 1 道样稿确认。据此重写资料分析 23 道（样稿第76题 + 22 道），全库达 135/135。

2. **配图按 MD5 分组读**：22 道中 15 道带配图，去重后只有 7 张图（一篇材料出多题）。按 MD5 分组，同材料一起取数、一起验算，比逐题下载快数倍。**教训**：资料分析是"材料组"结构，先分组再读图。

### 6.16 言语理解 40 道：借技能破"语感黑箱"，理性拆解

**修复**：新增 `visibleChildren(n)` 公共入口——`isExample` 节点必须 `exMatch((n.examples||[])[0])` 才返回，非例题节点恒显示（无题目对象的例题节点保守显示）；`layout()` 的 `place`/`scan`/`sh` 与 `render()` 的 `walk` 四处统一改用它。布局与渲染同源，避免筛选后隐藏节点仍占位。筛选 change 本来就调 `render()`，故一处改动三种筛选（试卷/对错/真题模考）全生效。`ignoreFilter` 旁路（例题节点点击、关联例题跳转）不受影响——那是弹窗层逻辑，与导图节点可见性解耦。

**验证**：`ui_probe.py filter` 专项 9/9（试卷 64→10、对错 64→35、模考 64→12 + 三态复位 + JS/404），smoke 6/6、方法面板 10/10、文档面板 4/4 全回归通过。把筛选回归固化成 `ui_probe.py filter` 子命令，以后展示改动必跑。

**教训**：① 数据结构升级（隐藏 examples→可见节点）时，要逐一复核所有消费该数据的下游——尤其"筛选/计数/可见性"这类横切关注点，弹窗改了不代表导图也改了；② 布局与渲染必须用同一个"可见子节点"函数，否则节点隐藏了但仍占位、出现空白；③ 验证要覆盖"筛选态"而不只是默认态（同 6.36 关联例题筛选态 bug 的教训），默认态永远 PASS 会漏掉整类筛选 bug。

### 8.4 部署脚本二进制图片支持（重要修复）

`gh_upload_curl.py` 旧版在读取阶段强制 `data.decode('utf-8')`，遇到 PNG 文件头 `0x89` 直接 `UnicodeDecodeError` 崩溃。修复方案：

- 按扩展名区分：`.json/.js` 等文本走 `encoding:utf-8`（大 JSON 用 utf-8 直传，避免 base64 被代理误判 400，失败再回退 base64）；`.png/.jpeg/.jpg/.pdf` 等走 `base64.b64encode(data).decode('ascii')` + `encoding:base64`。
- `BINARY_EXTS` 维护二进制扩展名集合，`is_binary()` 判断。
- dry-run 会打印每个文件的 encoding，便于上线前核对。

### 8.5 两次教训（务必警惕）

1. **样稿"展示"≠"入库"**：四科样稿题（8/41/62/96）当初只做了 JSON 展示给用户确认，后续批量注入的 19 题**不含**这 4 题，导致第一次部署后线上只有 19 题。发现方式：按 `src` 含"2023"统计只得到 19 条，且用题干独特文本全文搜索确认 4 题题干确实不在库。**结论**：样稿确认后必须把样稿题一并纳入注入清单，交付前用 `src`/题干双重统计核对题数与题号，不能只信"批量注入成功"。
2. **`data.js` 前缀反复丢失**：`load_json_with_js(DATA_DEMO)` 读的是 `data.json`，返回的 `js_prefix=None`，若用它写回 `data.js` 会把 `window.MM_DATA = ` 前缀丢掉，变成纯 JSON。**修复**：注入脚本里 `js_prefix` 写死为 `'window.MM_DATA = '`；每次部署前检查 `data.js` 开头必须是 `window.MM_DATA = `、结尾必须是 `};`，且正文（去前缀去分号）MD5 与 `data.json` 一致。

### 8.7 弹窗 UI 调整：解析顺序 + 分隔条可拖动（commit f7ec03a）

**需求**：例题弹窗的 v2 朱批解析调整区块顺序（深度解析→最优解→解题步骤），并让题目/解析之间的分割线可拖动。

**实现要点**：

1. **区块顺序**：`renderZpSolution()` 里把 `.zp-deep`（深度解析）、`.zp-strategy`（最优解）两段移到 `.zp-cols`（解题步骤/错因双栏）之前，并**同步重编序号**为 壹·深度解析 / 贰·最优解 / 叁解题步骤 / 肆错因——只挪位置不改序号会导致编号乱序，这是易漏点。

## 九、可复用的方法论

把整个项目提炼为可迁移到类似任务的通则：

1. **先存档，再动手**：任何改造前先建立带校验的不可变基线，保证可回溯。
2. **用最小实验验证核心假设**：本次用 20 KB 的 `minimal.html` 验证了"换数据不换引擎"这一最关键假设，成本极低、收益极高。
3. **解耦要验证，不能只声明**：用"两套数据 + 静态/动态双数据源"实际检验解耦是否成立。
4. **用真实数据做最终验证**：示例数据会掩盖层级、体积、性能等真实问题。
5. **UI 迭代以用户反馈为准绳**：主体优先、控件克制、触屏单独适配，都是多轮反馈沉淀的结果。
6. **网络受限时找 API 替代方案**：`git push` 不通就用 Contents API；不要卡死在一条路上。
7. **测试超时先隔离环境因素**：拦截非关键资源，区分"逻辑错"和"网络慢"。
8. **先低成本验证价值，再投入重基础设施**：demo 链接先行，自动部署后置。
9. **敏感凭据用后即焚**：权限过大的 token 完成使命后及时撤销。
10. **降噪优于加料**：提升专注力的有效手段从来不是增加元素，而是**把装饰性的亮拿掉、只留结构性的亮**。本次画布改造把 5 个高饱和模块色块缩成 3px 色条、层级改由明度承担、连线统一低对比，视觉噪声降下来后，同一屏内容反而更容易看清。
11. **给注意力装一盏探照灯**：静态全图（200+ 节点）天然让人失焦。焦点模式（点节点→高亮根到该节点路径、其余退暗）把"看什么"的决定权交还给用户，是画布类产品性价比最高的专注力手段。
12. **先判断信息层级，再谈美化**：用户嫌"太长要滚动"时，真正的问题往往不是长度，而是**把辅助信息做成了主角**。先回答"谁是重点"，重点做大、非重点压成一行小字或直接删除，比压缩字号有效得多。
